evolve is a search over agent configurations. You give it a seed agent, a way to vary one, and a way to score one; it proposes candidates, runs them in isolation, and keeps what wins.

What this is and is not. Lilian Weng's Harness Engineering for Self-Improvement argues that the near-term path to recursive self-improvement runs through the harness — the system around the model — rather than the weights, and that the binding constraint is the verifier. This is not that loop. It is the substrate underneath one: a composable API for varying, isolating, identifying and scoring agent configurations, with a human standing in for the verifier because that is the part nobody has solved. Nothing here improves itself.

The loop

Propose picks parents, recombines their genes, and applies a variation operator. Gate validates the result before anything expensive happens — a malformed candidate dies for the cost of a subprocess rather than a model run. Evaluate runs each survivor on the task in its own isolated checkout. Score turns a run into a number. Select decides who continues.

The budget is the design constraint

Every evaluation is a full agent session. A generation of five candidates on one task is five sessions; a search is tens of evaluations, not the millions an evolutionary algorithm normally assumes. Almost everything else here follows from that: the gate exists so bad candidates cost nothing, deduplication exists so nothing is paid for twice, and the search algorithms stay deliberately simple because at this sample size sophistication cannot express itself.

tenon deliberately refuses to do evaluation, scoring or selection. That refusal is why the search is a separate tool sitting on top rather than a feature inside it.

The loop is fixed. Five points in it are commands you supply — each reads one JSON object on stdin and prints one on stdout. Everything specific to your search lives there.

pairwhich parents reproduce tournament
combinewhich gene comes from which parent uniform
operatorshow a child varies no default
scorefitness no default
selectwho survives elitist

score and operators ship no default on purpose. A default fitness function would be the tool inventing an objective — precisely the move that makes a loop like this report progress it has not made.

What a hook actually receives and returns

pair is given the population and how many offspring are wanted, and returns one entry per offspring. A single parent reproduces asexually; two or more recombine. Returning tuples is what lets one policy express both who breeds and how often crossover happens, instead of splitting that across two settings.

→ in   { "generation": 2, "count": 5,
         "population": [ { "index": 0, "genome": "sha256:…", "score": 0.75,
                           "tags": {}, "genes": ["instructions.md", "skills/alpha"] }, … ] }

← out  { "pairs": [ [0], [0, 1], { "parents": [1], "tags": {"island": 2} } ] }

Parents are referenced by slot index rather than genome id, because two slots can hold the same genome and an id would then be ambiguous.

The other four contracts
hookreturns
combine{"genes": {"skills/alpha": "sha256:…"}} — a plan of which parent supplies each locus. Or {"materialized": true} if the hook wrote the child directory itself, which is the escape hatch for recombining below the component grain.
operatorsNot a hook but a weighted list of commands, each run with the candidate as its working directory. Each is named, and the name lands in the lineage, so the record answers which kind of change produced the gains.
score{"score": 0.7}, optionally with "tags" observed at runtime — which is how a behavioural descriptor arrives.
select{"population": ["sha256:…", …]}, or entries carrying tags. It may return the same genome twice.

One thing is not injectable

Validation. Every candidate passes through tenon before it can be scored, and that is what keeps a genome's identity meaningful — a fingerprint is only ever reported for a configuration that actually loads. Make the gate a policy and the identity stops certifying anything.

Because the points above are just commands, the search algorithm is a choice you make from outside rather than a property of the tool.

Slots carry tags, and the search never reads them

The population is a list of slots, not of genomes. A slot holds a genome plus an opaque tag dictionary that policies write and evolve only carries and inherits.

The distinction is load-bearing. A genome is content, addressed by its fingerprint and immutable, so its score belongs to it. An island, a niche, an age layer belongs to the slot — because the same content can occupy two at once. An island reset seeds the weakest island from the strongest, and afterwards one genome sits in two islands with one score. Put the tag on the genome and that becomes unrepresentable.

The island model, in full

Two policies and no change to evolve. pair groups the population by its island tag, draws both parents from within one, and tags the child with that island. select keeps each island's own best, and every third generation replaces the weakest island's members with copies of the strongest island's — which is the move that makes the model work, and the reason a genome has to be able to occupy two slots.

Genomes can change shape

Crossover only shuffles loci the parents already hold, so on its own the genome's dimensionality is frozen at whatever the seed had. An operator that adds a gene is how an agent acquires a capability rather than rewording an existing one; one that removes a gene is the counterweight, since growth without pruning is bloat.

Differently-shaped genomes still recombine because loci are aligned by name: skills/alpha in two genomes descends from one origin, so the name serves as the historical marking that says which genes correspond.

A search needs a representation — something to mutate, something to recombine, something to call the same or different. That came for free from how tenon already defines an agent.

An agent is a folder, so a genome is a directory

tenon defines an agent as plain files: an instructions.md plus typed directories. Nothing is registered; capability is added by adding a file. The search inherits its unit rather than inventing one.

Because a gene is a whole authored component, crossover is file-level recombination rather than text surgery: for each locus either parent holds, the child inherits one parent's copy intact.

The fingerprint is the identity

tenon computes a content-addressed digest over every authored input, and reports it only for a project that actually loads. One call both gates a candidate and names it — stable diagnostic identifiers on rejection, the fingerprint on success. Three things follow:

  • A cheap gate. Recombination produces incoherent offspring routinely — a skill whose tool did not come along. They die before a model is opened, and the rule that rejected them is recorded by name.
  • Deduplication. A genome already scored is never paid for twice, and a mutation that cycles back to a known genome is caught across generations.
  • Attribution. The same fingerprint travels on every run, so a score cannot drift apart from the configuration that earned it.

Isolation

Every candidate gets its own git worktree on its own branch. Variants cannot see or corrupt one another, the agent is free to write files, and promoting a winner afterwards is a plain git checkout. Worktrees are reclaimed once a generation is scored, so disk holds one generation rather than all of them.

Reproducibility

A folder cannot express which model ran or which harness version. A tenon manifest pins those — and it binds an expected fingerprint, which means it is bound to one genome, while every mutation changes the fingerprint. So the search writes one manifest per genome: many genomes crossed with one pin set. Two runs that look identical then really are, and the difference you observe is the change you made.

How we found that out

By getting it wrong. The first live run wrote one manifest from the genome directory, whose name is a fingerprint, and applied it to an agent directory named demo-agent. tenon refused every variant with manifest.drift.agent — failing closed, exactly as designed, on a mistake in how the manifest was generated.

Scoring is where a loop like this starts lying to itself. Weng's point is that the verifier is the bottleneck; this demo answers it by not automating the verifier at all.

Ask for a comparison, not a score

Absolute scoring is the wrong question to put to a person. How good is this, from 0 to 1? drifts with mood, order and fatigue. Which of these two is better? is the judgement people are reliable at, so the demo asks only that.

On the name. The pairwise-preference framing is borrowed from PAPRIKA (Training a Generally Curious Agent, ICLR 2025), which builds trajectory preference pairs and feeds them to DPO to fine-tune weights. This is not that. The same preference signal is consumed as fitness over agent configurations, and no weights are touched.

From ordinal to cardinal

Comparisons are ordinal; a search needs a number. The projection is Bradley-Terry maximum likelihood — fit a latent strength per genome such that P(i beats j) = pᵢ / (pᵢ + pⱼ), solved by Zermelo's iteration. Fitness is the fitted probability of beating a uniformly drawn opponent.

Why not just count wins

A raw win rate treats every comparison as equally informative, so beating the weakest entry counts the same as beating the strongest, and it has no answer at all when some pairs went unjudged. Two genomes with identical 1-1 records score 0.669 and 0.358 under the fit when their opponents differed in strength — where a win rate gives both 0.500.

The estimator is also honest about what it cannot know: going 1-1 against the same pair of opponents is genuinely uninformative — those likelihoods differ only by a constant — and it returns equal strengths rather than inventing a difference.

The anchor, and why the scale is global

A round's scores are normalised inside that round's field, so they do not compare across generations. A genome that went 5/5 against weak siblings and 1/5 against strong ones has not changed — its opposition has. That is not hypothetical; it is what the run below did.

So the incumbent is re-judged in every round. That shared entry links the rounds into one connected comparison graph, which makes a single fit over every comparison identifiable. It is the only basis on which a generation-1 genome and a generation-2 genome can honestly be compared.

The demo run. 360122bb won generation 1 outright at 5/5, then was re-judged inside generation 2 against its own children and came last at 1/5 — the anchor revealing that the field had improved, not that the genome had got worse.

Two smaller decisions

Re-judging corrects luck. Elitist selection on a noisy score keeps whichever candidate drew luckiest and never revisits it. Because the fingerprint names content, re-running an incumbent adds samples to the same genome and its estimate tightens rather than staying frozen at first contact.

An unjudged genome scores 0.5, not 0. The seed has nothing to compare against in generation 0. Scoring it zero would mean anything at all beats it — and whether the search beat the seed is the first question it has to answer.

How a human is wired into a machine API

This is the part that connects back to the API. The search calls its scoring command once per run, sequentially, after the generation has finished. A pairwise judge cannot answer the first of those calls without seeing the others — and the search is blocked waiting, so the others never arrive.

The way out is for the judge to not depend on its callers at all. By the time scoring starts, every variant's output is already on disk — so the first call makes the server read the whole generation itself, run the round robin in your browser, and answer every blocked caller from the result. The scoring command stays a dumb client that blocks on HTTP.

Nothing in the search knows a human is involved. It sees a command that takes a run on stdin and prints a number — the same contract a test-suite scorer satisfies. That is the sense in which this is an API rather than a feature.
